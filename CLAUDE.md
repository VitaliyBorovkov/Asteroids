# CLAUDE.md — Asteroid → Black Hole (steroid.io)

## О проекте
Unity-прототип. Игрок управляет астероидом в космосе, цель — вырасти через столкновения с другими астероидами до чёрной дыры, поглощающей всё на пути. Point-and-click управление, камера масштабируется по мере роста игрока.

Полный технический бриф — в `game-design.md` в корне проекта. Сверяйся с ним по архитектуре, формулам и структуре дерева талантов перед тем, как придумывать что-то своё.

## Стек и архитектурные решения
- Unity + C#. Разработчик уровня junior; код пиши уровня middle, объяснения давай пошагово, без лишней абстракции.
- DI: **VContainer** (НЕ Zenject/Extenject — тот заморожен с 2022 года). `LifetimeScope`, явные биндинги через `Configure`/installer.
- Реактивность: **R3** (НЕ UniRx — legacy, автор сам рекомендует мигрировать). Изменяемые статы — `ReactiveProperty<T>`.
- Async: **UniTask** вместо корутин (таймеры ивентов и т.п.).
- Addressables НЕ используется — прямые ссылки на префабы или `Resources`.
- Детали core loop (формула ударов, рост массы, визуальные стадии, дерево талантов, гравитация) — см. `game-design.md`, не дублирую здесь, чтобы не рассинхронизировалось.

## Правила кода
- SOLID, OOP, KISS, DRY, Unity best practices.
- Числовые параметры баланса (`step` формулы ударов, стоимости апгрейдов, радиусы притяжения) — в ScriptableObject или сериализуемые поля, не хардкодить. Должно быть удобно тюнить в инспекторе.
- Логи в консоль — только на английском, через `private const string LOG_PREFIX = "ScriptName";`.
- Тесты: Unity Test Framework, только Edit Mode, только чистая логика без MonoBehaviour (формула ударов, пороги стадий роста, расчёт стоимости апгрейдов). MonoBehaviour-поведение и ощущение геймплея тестами не покрываем — проверяется руками.

- Читай существующий код перед изменением. Правки — локальные: меняй только то, что нужно для задачи.
- НЕ дампи полный текст скрипта в ответ — редактируй файлы напрямую, кратко опиши, что изменил и почему.

После каждого изменения пиши: что проверить в Unity Editor, какие баги вероятны (пропущенный биндинг VContainer, неверный scope `LifetimeScope`, порядок инициализации `ReactiveProperty`, забытый `[Inject]` на объекте, созданном через обычный `Instantiate` вместо фабрики контейнера) и как их избежать.

- Не выдумывай Unity API — сверяйся с реальной версией движка в проекте.
- Коммить маленькими осмысленными шагами, чтобы неудачный шаг легко откатывался.
- Сообщение коммита — короткое и понятное: одна строка, что сделано и зачем, без описания хода работы и без перечисления всех задетых файлов (это видно из диффа). Императив, без вводных слов ("добавил", "исправил", "переименовал" — не "добавление", не "данный коммит делает...").
